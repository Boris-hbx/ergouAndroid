## Context

记账功能是二狗 App 核心模块之一，涉及多个页面（ExpenseScreen 列表页、ExpenseDetailScreen 详情页）、多个 ViewModel（ExpenseViewModel、ExpenseDetailViewModel）、外部 API（Next 后端 CRUD + Claude AI 收据解析）、以及聊天工具（4 个 Tool）。

当前记账功能存在多个 bug，但缺乏系统性的测试覆盖。本次变更不涉及代码修改，而是设计一套完整的端到端手动测试用例矩阵，配合 3 组真实测试数据，用于回归测试和新功能验证。

## Goals / Non-Goals

**Goals:**
- 设计一套可重复执行的 E2E 手动测试用例集
- 覆盖记账功能所有用户操作路径：CRUD、照片、AI 分析、批量处理、聊天工具
- 使用 3 组真实收据照片作为固定测试数据，确保测试可复现
- 每个测试用例包含：前置条件、操作步骤、预期结果、验证点
- 测试用例可作为后续自动化测试的 spec 基础

**Non-Goals:**
- 不编写自动化测试代码（本次只设计用例）
- 不修复已知 bug（测试用例用于发现和回归验证 bug）
- 不涉及性能测试或压力测试
- 不涉及 UI 截图对比测试

## Decisions

### 决策 1：测试用例以 E2E 为粒度，不拆分单元测试

**选择**：所有测试用例从用户操作入口到最终数据验证，走完整链路。

**理由**：记账功能的 bug 多发生在链路衔接处（如 AI 解析后的数据如何传递到保存接口、照片上传与条目创建的时序等），单元测试无法覆盖这些集成点。E2E 用例能最真实地模拟用户使用场景。

**替代方案**：分层测试（ViewModel 单测 + Repository 单测 + UI 测试）——更细粒度但无法覆盖链路问题，且维护成本高。

### 决策 2：使用 3 组固定测试数据

**选择**：
- Group 1（4 张照片）：同一 T&T 收据的不同部分 → 测试合并分析
- Group 2（5 张照片）：5 家不同商家的独立收据 → 测试独立分析
- Group 3（9 张照片）：Group 1 + Group 2 混合 → 测试最复杂场景

**理由**：固定数据确保测试可复现，不依赖用户实时拍照。3 组数据覆盖了从简单到复杂的递进场景。真实收据（含中英文、不同商家格式、不同金额量级）比造假数据更能暴露 AI 解析的边界问题。

**数据特点**：
| 收据 | 商家 | 金额 | 特殊点 |
|------|------|------|--------|
| T&T（4 张拼接） | T&T Supermarket #028 | $235.76 | 长收据需拼接，含中英双语商品名，多品类（肉/海鲜/蔬菜/点心） |
| Structube | Structube | $607.94 | 大额家具，含订单号和 Interac 支付 |
| Costco Gas | Costco Wholesale | $84.63 | 加油站收据格式特殊（升/单价/总价） |
| Food Basics | Food Basics | $19.56 | 小额超市，少量商品，简洁格式 |
| IKEA | IKEA Vaughan #372 | $44.89 | 含 SALE 折扣商品，含 QR 码 |
| 兰州拉面 | Gol's Lanzhou Noodle | $75.77 | 餐饮含 tip，金额=68.88+6.89 |

### 决策 3：测试用例按功能域分组，而非按页面分组

**选择**：按功能域分组（新建、照片、AI 分析、编辑、删除、聊天工具）。

**理由**：同一功能域的测试用例共享前置条件和测试数据，便于批量执行。按页面分组会导致跨页面流程（如列表→详情→返回列表验证）被拆散。

### 决策 4：混合照片场景设计为"发现问题"而非"期望成功"

**选择**：Group 3 的测试场景明确标注预期行为是"结果不理想，需要用户手动处理"。

**理由**：当前系统不支持 AI 自动识别哪些照片属于同一收据。混合照片无论选"同一单据"还是"不同单据"都无法完美处理。测试用例应如实反映系统限制，而非假装功能完善。同时也记录了"推荐分批处理"的正确流程。

## Risks / Trade-offs

**[测试数据依赖 Claude API]** → 涉及 AI 分析的测试用例需要有效的 Claude API Key 且产生实际 API 调用费用。缓解：AI 分析类用例标注为"需 API"，无 API 时跳过该类用例。

**[测试数据固定但 AI 结果不确定]** → Claude 对同一张收据的解析结果可能因模型版本更新而变化（如商品名/金额精度）。缓解：验证点以"金额在合理范围内"和"关键字段不为空"为标准，不做精确字符串匹配。

**[手动测试效率]** → 完整执行全部用例预计耗时较长。缓解：用例分优先级（P0 核心路径 / P1 边界情况），日常回归只跑 P0。

**[网络依赖]** → E2E 用例依赖 Next 后端和 Claude API 可用。缓解：网络相关失败场景单独分组，可在断网条件下专门测试。
